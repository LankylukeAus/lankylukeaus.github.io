What I learned

  • Validate assumptions before committing time to brute force.
  • Revisit exposed services when an access path becomes unstable.
  • Preserve naming, timing, and authentication context across pivots.
  • Account for latency and session behaviour through nested tunnels.
  • Separate confirmed evidence from inferred attack paths.

Defensive themes

00Attack path

→ mutual-TLS webmail → Wei Zhang administrator PFX
→ AD CS certificate mapping → Toby Ellis authentication

Assisted completion: Administrator AES key → Kerberos TGT → WMI / SMBExec

Handler was a layered Windows and OT lab. The independently verified chain reached Toby Ellis’s smartcard identity and triggered the operational event that created Kofi Asante’s session. The intended relay after that event remained unresolved; the final flags came from a separately documented assisted Kerberos path.

01Initial access and environment

HTB supplied the ext.dmalik account and an OpenVPN profile in Dmalik-PC01.zip. I updated the profile for the current Handler address on TCP/8443 and kept my default route unchanged. The internal HTB Airways range was 192.168.37.0/24.

export BOX_IP='<CURRENT_HANDLER_IP>'
sudo openvpn --config Dmalik-PC01.ovpn --pull-filter ignore redirect-gateway

The lab was roughly seven hours ahead, and Kerberos required FQDNs. Adding the domain hosts locally and running ticket-based tooling through faketime avoided clock-skew errors.

DC01Domain controllerKerberos, LDAP, SMB, WinRM, AD CS and webmail
SRV01Operations serverSMB, RDP and WinRM
SRV02OT access pointMSSQL and the OT VPN endpoint

02Credential Roaming and DPAPI

NTLM was disabled, so I obtained a Kerberos TGT for ext.dmalik and enumerated LDAP using that ticket. Wei Zhang’s directory object exposed msPKIDPAPIMasterKeys and msPKIAccountCredentials: Credential Roaming data containing a DPAPI masterkey, certificate material and a CNG private-key container.

k impacket-getTGT -dc-ip 192.168.37.1 'htb-airways.htb/ext.dmalik:HTB-AirwaysAudit2026!'
export KRB5CCNAME="$PWD/ext.dmalik.ccache"
k nxc ldap 192.168.37.1 -k --use-kcache --users

I extracted the wrapped records and converted the masterkey for John. The decisive detail was selecting the post-Windows-10-1607 domain context, domain1607+. The older context exhausted the wordlist; the correct context recovered Wei’s password in about 32 seconds. Hashcat rejected the context-3 format, while John processed it successfully.

Key lessonWhen DPAPI cracking fails, validate the SID and domain context before changing wordlists or tooling. Context selection was the foothold correction here.

03Webmail and the administrator certificate

The roaming data held a CNG private key protected by DPAPI. After decrypting the masterkey, reconstructing the RSA key and validating it against the roamed certificate, I produced webmail-access.pem and webmail-access.pfx. That client certificate enabled mutual-TLS access to Roundcube.

Wei’s mailbox contained a self-addressed backup with w.zhang.adm.pfx, an empty-password archive identifying the w.zhang.adm administrator identity. A second message provided the business context for Toby Ellis’s smartcard access and BHS monitoring.

04AD CS and smartcard authentication

As Wei, I enumerated certificate services and found the HTBA-SmartcardLogon template. It supported Smart Card Logon and Client Authentication, carried NoSecurityExtension, and was enrollable by Wei. Effective-rights testing showed that Wei could modify Toby Ellis’s altSecurityIdentities attribute but not reset his password or change other account properties.

I enrolled a smartcard certificate and created an exact issuer-and-reversed-serial mapping on Toby’s account. Certificate authentication returned a valid Toby TGT. The certificate subject remained Wei, so the explicit mapping—not a Toby UPN—was what established the authenticated identity.

X509:<I>DC=htb,DC=htb-airways,CN=htb-airways-DC01-CA
<SR><REVERSED_SERIAL>

Toby’s RDP session authenticated successfully but was unstable after the reset: it reached Local Session Manager and then terminated after roughly 50 seconds with ERRINFO_LOGOFF_BY_USER. Smartcard traces confirmed certificate use, so I treated this as a session-creation issue rather than a failed identity mapping.

05OT VPN and PLC event

Wei’s Sent folder included Staff-Access-OT.ovpn, providing access to 172.16.20.0/24 through SRV02. BHS documentation on SRV01 described the S7comm PLC, its DB1 layout and the conditions for a latched jam.

ControlDB1 locationRole
PE-01byte 16Photoeye input
JAM flagbyte 19Latched jam state
System modebyte 23Manual-mode control
Maintenance keybytes 40–43Required for mode changes

The procedure set maintenance mode, held the PE-01 signal high and confirmed that the JAM flag latched. A seven-second loop initially failed because writes crossed two VPN layers from Australia. Extending the loop to 30 seconds delivered 32 writes and produced the expected operational event.

06Kofi’s session and the unresolved relay

Within about 30 seconds of the jam, Terminal Services enumeration on SRV01 showed Kofi Asante’s session as active. This confirmed that the PLC event was the correct trigger.

Session 0  Services        disconnected
Session 1  Console         connected
Session 2  k.asante        active

The intended follow-on appeared to depend on Kofi’s temporary session connecting to an internal SRV02 service, followed by authentication relay or redirection. I investigated DNS, MSSQL and session activity but never observed the required outbound connection. This remains the unresolved portion of the intended route.

07Assisted completion

Completion provenanceThe final flags were recovered using a static domain Administrator AES-256 key supplied by Nate. This was an assisted route and is not presented as an independently discovered escalation.

The supplied key produced an Administrator Kerberos TGT. Kerberos-authenticated WMI recovered the root flag from DC01. On SRV01, WMI failed at the DCOM stage despite working SMB and Kerberos authentication, so Kerberos-authenticated SMBExec was used to obtain the user flag.

k impacket-getTGT -aesKey '<Administrator AES-256 key>' -dc-ip 192.168.37.1 htb-airways.htb/Administrator
export KRB5CCNAME="$PWD/Administrator.ccache"
k impacket-wmiexec -k -no-pass 'htb-airways.htb/administrator@dc01.htb-airways.htb'
k impacket-smbexec -k -no-pass 'htb-airways.htb/administrator@srv01.htb-airways.htb'

08Practical takeaways

  • Validate DPAPI context, SID and cryptographic assumptions before investing in longer cracking runs.
  • Separate proof of authentication from proof of an interactive session; Toby’s certificate mapping worked even though RDP was unreliable.
  • Account for latency in OT control loops. A technically correct sequence may still fail if its timing does not survive the network path.
  • Restrict and monitor Credential Roaming reads, certificate-template enrollment, altSecurityIdentities writes, smartcard logons and OT register writes.
  • Keep exportable administrator certificates out of email, use hardware-backed keys where possible, and rotate exposed Kerberos keys immediately.

09Conclusion

Handler combined Credential Roaming, DPAPI, CNG private-key recovery, mutual TLS, AD CS, certificate mapping, nested VPN access and S7comm interaction. The main lesson was methodological: verify the exact cryptographic context, distinguish observed evidence from inference, and document the point where a route becomes unstable. The DPAPI-context correction unlocked the central path; the final relay remained unresolved, while the assisted Kerberos route completed the machine.
